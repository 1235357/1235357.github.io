# A balanced document workspace

The previous workbench placed document upload, model preparation, chunking,
embedding, question controls and historical receipts in one long left column.
The answer panel and full-width notebook followed that column's height, leaving
a large blank region after the shorter answer panel. The revised layout gives
document preparation its own full-width row and aligns the question and answer
cards beneath it.

Applied design guidance: the installed official Emil Kowalski
`emil-design-eng` skill, including coherent defaults, visible press feedback,
keyboard focus, readable controls and purpose-driven motion. Native disclosures
open immediately; no decorative opening animation delays repeated inspection.

| Before | After | Why |
| --- | --- | --- |
| Every preparation and question control occupied the left column | Upload and passage preparation share a full-width document row; question and draft sit below | Reading follows document → question → result without a tall sidebar determining the entire page |
| Model predownload controls and source-cell fields dominated the initial view | Optional preparation and source comparison have native, initially closed disclosures | Primary actions remain visible; advanced work stays available on demand |
| Document, passage and query receipts extended the left column | Complete receipts live inside the computation notebook | Evidence stays preserved alongside the computation it explains |
| Transparent left panel versus a white answer panel | Both question and draft use the same white surface, border, padding and radius | Align the visual weight as well as the top edge |
| Large empty output text reserved additional space | A compact, readable empty-state panel | The initial layout describes the next action without an oversized placeholder |

The original input IDs and explicit work/download actions remain intact.
Preparation and generation descriptions distinguish total verified asset bodies
from missing files actually fetched. Source comparison remains independent of
the native generation artifact. Reordering presentation does not establish
financial correctness or change the session's acceptance rules.

The later information-hierarchy revision follows the user's reference
[Yingda Yu profile](https://yingda-yu.github.io/Dean-Yu-050325.github.io/), inspected
in the Codex browser. Its portrait, short positioning statement, two primary
entrances and selected-content sections informed the hierarchy; its biography
and claims were not reused. Primary-source guidance from
[NN/G's Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
supports keeping common actions visible, giving specialized controls clear
secondary entrances, and avoiding excess disclosure levels.

The six-stage rail is now a native disclosure. The primary question card keeps
its question and Run controls; Top K lives in its retrieval settings. Context
assembly and Generate answer sit beside the draft. Generator configuration and
lifecycle trace sit with the notebook's existing complete receipts. Cancellation
is visible while work is active. All actions still require their existing
explicit user events; no model work starts just because a disclosure opens.

The initial balance revision's Codex in-app browser checks cover local PDF selection, parser execution,
five accepted chunks and disclosure access. Local responsive measurements cover
390, 780, 1280, 1920 and 3200 CSS-pixel viewports: document client width equals
scroll width, body text remains 17 px Manrope, and visible button/summary targets
are at least 47.59 px high. At 1920 px, question and draft begin at the same
vertical coordinate, with heights 767.33 and 684.13 px. This is browser viewport
testing, not a physical-phone or subjective design-acceptance claim.

The complete figure-theme regeneration, export checks, final test suite and
publication evidence are recorded separately before release is accepted.

## Empty draft refinement

A later review of the actual public page against the same reference profile and
NN/G's original progressive-disclosure article found one remaining duplicate:
the initial session status and an empty native execution receipt both described
the absence of an answer. The generation view now retains its empty receipt
text internally but hides that container until a native result and inspection
exist. An accepted result restores the same complete presentation, including
refusals, raw output, citations and downloadable receipts. The initial draft
instructions are shorter, while the explicit 815.73 MB asset disclosure stays
visible before a visitor chooses Generate answer. This presentation refinement
does not start or repeat model work.
